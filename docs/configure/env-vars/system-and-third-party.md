title: System and Third-Party
description: Environment variables owned by your system or other tools that Claude Code reads, such as HOME, TERM, and ALL_PROXY.

Claude Code reads many variables that it does not define.
Your system, your terminal, CI services, and other tools own them.
Examples are `HOME`, `PATH`, `EDITOR`, `TERM`, and `ALL_PROXY`. Claude Code reads them to find files, pick colors, and detect where it runs.

This page lists 221 variables. You set many of them for your system anyway. Set them in your shell, or in the `env` key of a settings file.

## Example

```bash
export EDITOR="code --wait"
claude
```

Claude Code opens this editor for files, for example for `/memory`. `VISUAL` wins over `EDITOR`.

## How It Works

Many rows here are detection names. Claude Code checks whether a name is set to learn the terminal, CI service, or host. For example, `TRAVIS` or `GITLAB_CI` tell it that it runs in CI, which affects the terminal color level.
You rarely set these by hand. Set one only to fake or hide a detection result.

## How Plugin Eval Picks Credential Paths

`claude plugin eval` runs the eval cases of a plugin. When you grant `Bash` with `--allow-tools`, every command runs in a sandbox, and the [official page](https://code.claude.com/docs/en/plugin-evals.md#grant-tools) says that your home folder and Claude Code configuration are unreadable. Before the run, Claude Code writes a `settings.json` in the config folder of the run. Its `sandbox` block lists the credential files and the folders that Bash cannot read.

The program builds that list from your environment. It reads the variables in the rows that name `claude plugin eval`. It follows the files that some of them name, such as `git` config, Ansible config, `krb5.conf`, and Java options. It also adds the default places in your home folder.

A path that the program cannot make safe stops the run before any case starts. A relative path in a credential variable does this. The error text names the cause. A variable in the program's pointer list gives one shared cause: `a credentials pointer variable (AWS_CONFIG_FILE, GOOGLE_APPLICATION_CREDENTIALS, ANTHROPIC_CONFIG_DIR and the like) holds a relative path`. Other variables name themselves, for example `HF_HOME holds a relative path`.

This example uses a `netrc` file inside the plugin folder, which the sandbox may otherwise read:

```bash
export NETRC="$PWD/creds/netrc"
claude plugin eval . --allow-tools Bash
```

In a probe, a Bash `cat` of that file with `NETRC` unset printed the file. With `NETRC` set, the same command failed with `cat: ...: Operation not permitted`. A relative `KUBECONFIG` stopped the run with the pointer text above. The runs are `print.evalcreds.netrc.unset`, `print.evalcreds.netrc.set`, and `print.evalcreds.relative.KUBECONFIG` of `2.1.319`. Each ran the real binary against a local stub, with no model call.

The same probes showed that variables with rows on other pages take part in the same way, for example `AWS_CONFIG_FILE` and `GOOGLE_APPLICATION_CREDENTIALS` in [Cloud Providers](cloud-providers.md), and `GIT_CONFIG_GLOBAL` and `JAVA_TOOL_OPTIONS` in [Tools and Bash](tools-and-bash.md). Their rows do not repeat this effect.

More checks used the same probes. The ids are `print.evalcreds.anthropic-profile`, `.anthropic-profile-abs`, `.aws-credential-process`, `.aws-credential-source`, `.ssh-wildcard`, and `.pm` of `2.1.319`.

- `ANTHROPIC_PROFILE` does not choose which profile files are hidden. With `ANTHROPIC_CONFIG_DIR` set, the program hid the credential file of every profile in `configs`, with a profile `a` named. A value that is an absolute path or holds `..` stopped the run with `the selected Anthropic profile name leaves the configs directory`.
- An AWS config with `credential_process`, or with a `credential_source` other than `Environment`, stopped the run with `an AWS credential_process / credential_source cannot be excluded from the shell`. `credential_source = Environment` did not. A `web_identity_token_file` line hid the token file.
- An `ssh_config` `Include` with a wildcard in the folder part stopped the run with `an ssh_config Include pattern with a wildcard directory cannot be followed`.
- The settings list of hidden variables also takes names by value. In a probe, a variable whose value held a URL with a user and password was added, and so was a variable named with `PROXY` whose value held `@`. A variable without `PROXY` in its name that held `bar@baz`, and a plain proxy URL, were not. Only `EVAL_` variables were tested, because the program filters the other names of the run.
